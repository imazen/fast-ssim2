# fast-ssim2 0.9.0 — x86_64 bench record (2026-08-31)

**Purpose:** check whether the 0.9.0 API change (fallible `ToLinearRgb`, YUV
input routed through it instead of the removed `compute_frame_ssimulacra2`)
costs anything measurable.

**Answer: no measurable regression.** The one case that looked like a
regression — `ssimulacra2_320x240`, the smallest YUV input — has a run-to-run
spread on a *single unchanged build* that is larger than the difference being
attributed to the change.

## Setup

| | |
|---|---|
| Host | `r7900x` — AMD Ryzen 9 7900X (12C/24T, Zen 4), 29 GB RAM, Linux 7.0.0-30 x86_64 |
| Command | `nice -n 19 ionice -c 3 cargo bench --bench benches` (full suite, no filter) |
| Harness | zenbench 0.1.2 via `criterion-compat`; interleaved round-robin, so the bench set must not be filtered if runs are to be compared |
| Build | release profile from the workspace root (`lto = "thin"`, `codegen-units = 1`), **no `-C target-cpu=native`** |
| Commit under test | `68c22ee` (0.9.0) |
| Raw logs | `/tmp/fss2-bench-x86-090.log`, `-r2.log`, `-r3.log` on `r7900x` (ephemeral); numbers transcribed below |

The three `ssimulacra2_*` (non-`rgb`) cases feed `Yuv<u8>` 4:4:4, full range,
BT.709 / BT.1886 / BT.709. The `ssimulacra2_rgb_*` cases feed `yuvxyb::Rgb`.

zenbench printed `0 rounds ⚠ only 0 rounds` on every case in every run — it
could not complete its normal round budget, which is the likely source of the
instability at the smallest size. Treat single runs here as low confidence;
that is why three were taken.

## Measurements

### 0.9.0 (`68c22ee`), three consecutive runs

| Benchmark | run 1 | run 2 | run 3 | spread |
|---|---|---|---|---|
| `ssimulacra2_320x240` (YUV) | 7.5 ms | **8.2 ms** | 7.5 ms | **9.3%** |
| `ssimulacra2_1920x1080` (YUV) | 231.5 ms | 231.5 ms | 231.2 ms | 0.1% |
| `ssimulacra2_3840x2160` (YUV) | 965.9 ms | 965.0 ms | 962.6 ms | 0.3% |
| `ssimulacra2_rgb_320x240` | 8.4 ms | 8.4 ms | 8.4 ms | 0% |
| `ssimulacra2_rgb_1920x1080` | 312.2 ms | 312.1 ms | 311.7 ms | 0.2% |
| `ssimulacra2_rgb_3840x2160` | 1.31 s | 1.31 s | 1.31 s | 0% |
| `blur` | 5.4 ms | 5.5 ms | — | 1.9% |

### Owner's prior runs on the same host, same command

Two runs each, taken before the 0.9.0 API change landed. `main` here is
`f56991e`, i.e. **0.8.2 plus `82d9da8`** (the `SimdImpl` backend unification) —
not this release.

| Benchmark | v0.8.2 | `f56991e` |
|---|---|---|
| `ssimulacra2_320x240` | 7.5 / 7.8 ms | 8.5 / 8.1 ms |
| `ssimulacra2_1920x1080` | 231.2 / 230.2 ms | 230.3 / 229.7 ms |
| `ssimulacra2_3840x2160` | 960.3 ms | 957.6 ms |
| RGB (all three sizes), `blur` | flat | flat |

## Reading

- **`ssimulacra2_320x240` is unstable, not regressed.** Across eight runs of
  three different builds the value takes 7.5, 7.5, 7.5, 7.8, 8.1, 8.2, 8.5 ms.
  Two of those 7.5s and the 8.2 come from the *same* 0.9.0 binary. A ~0.7 ms
  band that a single build spans on its own cannot support a claim that a code
  change moved the number by 0.6 ms. The `+8–9%` that a v0.8.2-vs-`f56991e`
  comparison suggests is inside that band.
- **Everything else is flat**, and tightly so: 1080p and 4K YUV, all three RGB
  sizes and `blur` reproduce to ≤0.3% across runs and across all three builds.
  4K sits ~0.5% above v0.8.2's single 960.3 ms sample, which is within its own
  0.3% run spread plus a one-sample baseline.
- **Why the small case is the noisy one:** it is the only benchmark whose
  per-iteration time (7–8 ms) is short enough that zenbench's inability to
  complete its rounds (`0 rounds`) leaves the mean dominated by a handful of
  iterations. Fixed overhead — allocation, archmage dispatch, the YUV→RGB
  matrix setup — is also a much larger fraction of it than at 1080p/4K.

## What would settle it

Neither this record nor the owner's establishes a per-call fixed-overhead
number, because none of these runs completed zenbench's round budget. To
measure the 0.9.0 conversion path's fixed cost properly, fit
`total = α + β · pixels` across at least four sizes (≤64×64, 256×256, ~1 MP,
4096×4096) on a build where zenbench reports a completed round count, and
report α separately from β. That has not been done.
