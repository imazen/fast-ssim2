Two things stand out. The M4 Pro is **2–4× faster single-threaded** than every
x86 box here, including a Zen 5. And multi-threaded gain is **1.15–1.86× on
12–32 threads**, which is poor everywhere — `wsl` barely benefits at all, and it
is the same silicon as `r7900x`, so that gap is the WSL2 environment rather than
the CPU.

## What limits it — and a correction

An eight-instance test on the 16-core Zen 3 box: one single-threaded 4K run
takes 1075 ms; **eight concurrent single-threaded runs take ~3280 ms each**, so
eight cores buy 2.6× throughput rather than 8×.

That was first written up as "the metric is strongly memory-bandwidth bound".
**That reading is wrong for a single run.** One 4K run moves roughly 3 GiB in
1.06 s — about 2.8 GiB/s, a few percent of what the machine can stream. What the
eight-instance result shows is that eight instances, each with an ~800 MiB
working set, evict each other from a 64 MiB L3: a **capacity** effect that
governs batch throughput, not single-image latency.

The distinction decides what is worth building:

- **Batch throughput** (many images at once) is limited by working-set size.
  Fusing *across stages* — multiply → blur → map over a tile that stays
  resident — is the version of the locality idea that has not been refuted.
- **Single-image latency** (what the CLI does) is compute- and latency-bound.
  The levers are the remaining serial stages, wider SIMD where the hardware has
  it, and less arithmetic.

Directly refuted: that *bytes moved* is the cost model. Removing ~995 MiB per
scale of sequential, prefetchable traffic bought ~1% — see
[`fused_blur_negative_2026-09-10.md`](fused_blur_negative_2026-09-10.md).

## Ideas measured and not merged

Both live on branches with their full numbers, so neither gets re-attempted from
scratch:

| idea | branch | verdict |
|---|---|---|
| Vertical blur parallelised over pre-sliced column bands | `vertical-band-blur` | Helps 2 machines (M4 Pro −21%, wsl −13%), **hurts 4** (r7900x +25%, r5900xt +16%, i265 +14%, dev +11%). Not portable. |
| Streaming the horizontal blur into the vertical pass through a ring buffer | `fused-blur` | ST ±0% at 4K, −1% at 8K; **MT +45% worse**. The traffic it removes is free. |

The band work is not wrong — it is bit-identical, the serial path is unaffected,
and the technique (per-row `split_at_mut` grouped into bands) is sound and
needed no `unsafe`. It simply does not pay off portably, and the one policy knob
that governs it (bands per plane) has opposite optima on different machines.

## What is still worth trying

In rough order of expected value, given the above:

1. **Per-channel parallelism for `edge_diff_map`**, the last big stage still
   serial under `rayon`. Same shape as the `ssim_map` change already on `main`,
   which was bit-identical and cheap.
2. **AVX-512 (`v4`/`v4x`) arms.** Every kernel is `v3`-only, so `dev` (Zen 5,
   full-width 512-bit datapath) runs 256-bit code. Single-image latency is
   compute-bound, so this is the one place wider vectors should genuinely pay —
   and it is cheap to disprove on `dev`.
3. **Tiled stage fusion** for batch throughput, per the working-set argument
   above. Bigger surgery; only worth it if batch throughput is a goal.
4. **The power-of-two width residual**, still unexplained: 4096-wide costs +7.5%
   against 4104 even after the blur's de-aliasing fix
   ([`blur_stride_2026-09-09.md`](blur_stride_2026-09-09.md)). Two guesses have
   already measured zero; this one needs profiling, not another guess.
