# Is jpegli's cube root faster than ours? Yes — on both architectures

**Date:** 2026-09-09 · **Repo commit:** `737864b` · **Bench:**
`benches/cbrt_perf.rs` (in the study tree, sources in
[`version_divergence_2026-09-09/`](version_divergence_2026-09-09/)) ·
**magetypes:** patched to the local 0.9.29 / 0.9.28 worktree so
`f32x8::cbrt_midp` is available; the repo itself still pins 0.9.17.

Hosts:

| host | CPU | tier taken | toolchain |
|---|---|---|---|
| local | Apple M4 Pro (aarch64) | `neon` | rustc 1.98.0 |
| `r7900x` | Ryzen 9 7900X (Zen 4) | `v3` (AVX2+FMA) | rustc 1.98.1 |

Companion to [`version_divergence_2026-09-09.md`](version_divergence_2026-09-09.md),
which found that adopting jpegli's `CubeRootAndAdd` moves fast-ssim2 measurably
closer to the C++ binary. The open question there was what it costs. It does not
cost anything — it *pays*.

## The three cube roots

| kernel | seed | refinement | divides | lane round-trips |
|---|---|---|--:|--:|
| **shipped** (0.8.2+) | scalar per-lane bit hack, integer `/ 3` | 2 Halley steps on `x^(1/3)` | **2** | 1 `to_array`+`from_array` per chunk |
| **jpegli** | `kExpBias - (bits >> 23) * kExpMul` — vectorises | 3 Newton + 1 corrected step on the **reciprocal** cbrt | **0** | **0** |
| **magetypes** `cbrt_midp` | scalar per-lane bit hack (same shape as ours) | 2 Halley steps | 2 | 1, plus sign/zero blends |

jpegli iterates `x^(-1/3)` and recovers the root with `r*r*x`, so every step is
mul/mul/FMA — no `fdiv` at all — and its seed needs no integer division, so it
stays in registers instead of going through memory. That is the whole mechanism
behind the numbers below.

## Measurement

Full XYB conversion (opsin matmul → clamp → cube root → XYB transform) over a
deterministic LCG buffer in `[0, 1]`, three sizes, **three runs per host**,
`nice -n 19`, no `target-cpu=native`. The kernels are in-place and destructive,
so each timed iteration re-copies the input; a `copy_only` arm measures that
memcpy floor and every figure below has it **subtracted**. Medians of three
runs:

### aarch64 (M4 Pro, NEON)

| size | shipped | jpegli | magetypes `cbrt_midp` |
|---|--:|--:|--:|
| 4 096 px | 8 328 ns | **8 083 ns (−2.9%)** | 9 289 ns (+11.5%) |
| 65 536 px | 134.0 µs | **130.3 µs (−2.8%)** | 149.6 µs (+11.6%) |
| 1 048 576 px | 2 148 µs | **2 089 µs (−2.7%)** | 2 405 µs (+12.0%) |

### x86_64 (Ryzen 9 7900X, AVX2+FMA)

| size | shipped | jpegli | magetypes `cbrt_midp` |
|---|--:|--:|--:|
| 4 096 px | 7 626 ns | **7 563 ns (−0.8%)** | 8 399 ns (+10.1%) |
| 65 536 px | 132.2 µs | **121.4 µs (−8.2%)** | 133.6 µs (+1.1%) |
| 1 048 576 px | 2 051 µs | **1 924 µs (−6.2%)** | 2 089 µs (+1.8%) |

The ordering (jpegli fastest, `cbrt_midp` slowest) held in **all six runs at all
three sizes** — the one exception being x86 at 4 096 px, where jpegli's lead is
inside the run-to-run spread. Per-run spread is much wider on the 7900X
(±40–135 µs mad at 1 MP) than on the M4 Pro (±5–9 µs), so treat the x86
percentages as 3–9%, not as three significant figures.

`zenbench` printed `0 rounds ⚠ only 0 rounds` on every case — the harness quirk
already recorded in `CLAUDE.md` — so these are medians of repeated whole-process
runs, not zenbench's own paired CI.

## What this means

- **The most faithful cube root is also the fastest one.** The accuracy result
  (bit-exact with the C++ reference) and the speed result point the same way, so
  adopting jpegli's `CubeRootAndAdd` has no speed/fidelity trade-off to weigh —
  only the arch-consistency question (it is FMA-shaped) and the fixture re-pin,
  both listed in the companion record.
- **`magetypes::f32x8::cbrt_midp` is not the answer.** It is the same algorithm
  fast-ssim2 hand-rolls — Kahan bit-hack seed pulled out to a scalar array, two
  Halley steps, two divides — plus sign extraction and a zero blend we do not
  need, and it uses a different magic constant (`0x2a50_8c2d` vs our
  `709_958_130`). Measured 12% slower on NEON, ~1–2% slower on AVX2. Switching
  to it would be a dedup, and would cost time.
- **XYB conversion is one stage of the metric.** These are kernel timings; the
  end-to-end effect is this delta times XYB's share of `compute_ssimulacra2`,
  which is not measured here.

## Which C++ is "the" C++: all three are the same code

Checked, because the fidelity argument depends on it:

| implementation | `CubeRootAndAdd` | `FastGaussian1D` |
|---|---|---|
| `cloudinary/ssimulacra2` (the official standalone repo, `src/lib/jxl/`) | identical | identical |
| `libjxl` (`lib/jxl/base/fast_math-inl.h`, `tools/gauss_blur.cc`) | identical | identical |
| `jpegli` (`lib/base/fast_math-inl.h`, `tools/gauss_blur.cc`) | identical | identical |

The three differ only in include paths, namespace/macro spellings, and
signatures (`intptr_t width` vs `ptrdiff_t xsize`, `AlignedUniquePtr` vs
reference). Constants (`kC2 = 0.0009f`, the 108 weights), `SSIMMap`,
`EdgeDiffMap` and `Downsample` match as well. So "the jxl approach", "the jpegli
approach" and "the official SSIMULACRA2 approach" are one implementation, and
the parity findings against the Homebrew jpegli binary apply to all three.

**Correction to `cpp_parity_2026-08-31.md` §2.** It says bit-exact agreement
with the C++ tool "is not achievable in principle without also matching the
vector width it was built for". The horizontal Gaussian is capped at four lanes
on every target — `#define JPEGLI_GAUSS_MAX_LANES 4` /
`using D = HWY_CAPPED(float, 4)` — so its output does *not* vary with the build's
vector width; only `HWY_SCALAR` (which skips the unrolled body entirely) differs.
The rest of that section stands: the scalar and vector forms of the reference
disagree with each other, and ours matches the scalar one.

## Not measured

- **Whether jpegli's 4-unrolled horizontal blur is faster than ours.** That is
  the larger half of the accuracy win in the companion record, and it is
  currently blocked on `magetypes`: the C++ body needs `Broadcast<N>` (splat one
  lane) and `ShiftLeftLanes<N>`, and `magetypes` 0.9.29 `f32x4` exposes neither
  (it has `interleave_lo/hi`, `transpose_4x4`, `blend`, but no lane broadcast or
  lane shift). Emulating them through `to_array()` would measure the emulation,
  not the algorithm. A port that dodges both — precompute the four shifted
  coefficient vectors as constants, and splat each input sum from a scalar load —
  is possible with today's API and is the next step.
- **AVX-512.** Every kernel declares `#[magetypes(v3, neon, wasm128, scalar)]`,
  so a Zen 4/5 or Ice Lake+ machine runs the AVX2 path. Adding `v4`/`v4x` arms
  alone would mostly re-encode the same 8-lane code; a real win needs 16-lane
  bodies (`magetypes` has `f32x16`). Untested either way.
